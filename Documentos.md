# Documentação — MedVision AI

O MedVision AI é um sistema de análise de imagens médicas desenvolvido para a disciplina de Processamento de Imagens e Sinais. A ideia central é simples: o médico ou estudante carrega uma imagem de Raio-X, Ressonância Magnética, Mamografia ou Retinografia, e o sistema processa essa imagem, identifica regiões suspeitas e gera um laudo automático com a ajuda de inteligência artificial. O projeto foi construído em três partes que conversam entre si — uma interface visual no navegador, um servidor em Python e uma conexão com o modelo de IA Claude da Anthropic.

O desenvolvimento não seguiu um caminho reto. Começou apenas com a tela de análise, onde o usuário podia selecionar um algoritmo, ajustar parâmetros e ver os resultados. Nessa fase inicial, as imagens eram todas fabricadas pelo próprio código — o sistema desenhava elipses, gradientes e ruído no canvas do navegador para simular como seria um Raio-X ou uma RM de verdade. Era suficiente para testar a lógica, mas longe de ser um sistema real.

Com a estrutura base funcionando, o projeto cresceu para incluir o Histórico, os Relatórios e as Configurações. O Histórico registra cada análise feita, permite filtrar por tipo de exame ou resultado, e exporta os dados para CSV. Os Relatórios mostram gráficos com a evolução da precisão ao longo das análises e a distribuição por modalidade de exame. As Configurações permitem ao usuário personalizar o comportamento do sistema, como o limiar de confiança padrão, a cor das marcações de anomalia e se o sistema deve analisar automaticamente ao carregar uma imagem.

O caminho até chegar num sistema que funcionasse corretamente não foi sem tropeços. Três bugs especialmente difíceis apareceram durante o desenvolvimento e cada um ensinava algo diferente sobre como o sistema deveria se comportar.

O primeiro bug fazia o sistema classificar absolutamente todo exame como suspeito, mesmo os claramente normais. O motivo estava escondido numa linha aparentemente inofensiva: o status era definido com base em quantas anomalias estavam cadastradas no banco de demonstração, e esse banco sempre tinha anomalias. Não importava o que o usuário configurasse, o resultado era sempre suspeito. A correção foi mudar a lógica para considerar apenas as anomalias que passassem pelo limiar de confiança real configurado pelo usuário.

O segundo bug foi o oposto exato, e apareceu logo depois de corrigir o primeiro. Agora tudo dava normal. O limiar padrão estava configurado em 0.80, mas as confianças das anomalias ficavam entre 0.61 e 0.91. Com o ajuste de sensibilidade empurrando os valores um pouco para baixo, quase nenhuma anomalia conseguia ultrapassar o limiar. A solução foi recalibrar o valor padrão para 0.50, que é o ponto mais próximo do que se usa em sistemas clínicos reais, onde é preferível investigar um caso normal a deixar um caso doente passar.

O terceiro bug era o mais silencioso e por isso o mais traiçoeiro. As métricas de Precisão, Recall e F1-Score sempre mostravam exatamente 100%, em qualquer situação, com qualquer imagem. O problema estava numa divisão por zero que acontecia quando nenhuma anomalia era detectada — o código calculava zero dividido por zero e usava 100% como valor de segurança. Além disso, o conjunto de avaliação era pequeno demais, com apenas duas ou três anomalias, fazendo qualquer acerto virar 100% automaticamente. A solução foi simular um conjunto de avaliação maior, com aproximadamente 200 regiões da imagem, refletindo como modelos médicos reais são avaliados na prática.

Um problema que reapareceu em momentos diferentes foi a leitura incorreta dos sliders de parâmetros. Os identificadores no HTML estavam colocados nos elementos de texto que exibiam os valores visualmente, e não nos controles deslizantes em si. Quando o código tentava ler o valor de um elemento de texto, recebia indefinido, e qualquer cálculo com esse valor indefinido produzia resultados sem sentido — sem gerar nenhum erro visível, apenas resultados errados em silêncio.

Cada algoritmo de processamento foi pensado para transformar a imagem de uma forma diferente antes de tentar identificar anomalias. A Filtragem Gaussiana suaviza a imagem reduzindo ruídos, sendo mais indicada para imagens com muito granulado. A Segmentação Watershed analisa cada região da imagem comparando com sua vizinhança local, sendo mais eficiente para imagens onde o brilho varia muito de uma área para outra, como mamografias. A CNN Multiclasse calcula um mapa de saliência que destaca as regiões de maior variação de intensidade, funcionando como uma simulação visual de como uma rede neural enxerga a imagem. A Detecção Canny é especializada em encontrar bordas e contornos, sendo a mais precisa para delimitar regiões suspeitas mas também a mais propensa a sinalizar bordas normais como problemas.

As três métricas exibidas pelo sistema têm significados clínicos concretos e vale entender o que cada uma diz. A Precisão responde à pergunta de quantos dos casos sinalizados como suspeitos eram realmente suspeitos — uma Precisão baixa significa que o sistema está gerando muitos alarmes desnecessários. O Recall responde quantos dos casos doentes existentes o sistema conseguiu encontrar — um Recall baixo é o mais perigoso, porque significa que doenças estão passando despercebidas. O F1-Score equilibra as duas métricas numa nota só, sendo o número mais importante para avaliar o sistema como um todo, especialmente porque exames normais são muito mais comuns que suspeitos no mundo real.

A integração com a inteligência artificial foi o salto mais significativo do projeto. Antes dela o sistema apenas simulava resultados com base em regras fixas. Depois, ao carregar uma imagem real, o sistema envia essa imagem para o Claude com instruções específicas sobre o tipo de exame e recebe de volta um laudo estruturado com o status do paciente, o nível de confiança, os achados identificados e uma recomendação clínica. Um detalhe técnico importante foi proteger a leitura do retorno da IA, porque o modelo às vezes adiciona texto explicativo em volta do resultado, e o sistema precisa saber extrair apenas a parte que interessa independentemente do formato que vier.

O servidor foi construído como um arquivo único em Python para facilitar o uso tanto no Google Colab quanto no GitHub, sem precisar gerenciar várias pastas e arquivos ao mesmo tempo. Ele usa SQLite como banco de dados porque não exige instalação de servidor separado — o banco é simplesmente um arquivo que vai sendo criado e atualizado automaticamente. A versão assíncrona do SQLite foi escolhida porque o servidor precisa continuar respondendo a outras requisições enquanto espera o banco, e a versão comum bloquearia tudo enquanto aguardava. A validação dos dados recebidos é automática, então se alguém enviar um limiar de confiança com valor impossível, o servidor rejeita imediatamente com uma descrição clara do erro, sem precisar de nenhuma verificação manual no código.

Por fim, é importante deixar claro que o MedVision AI foi construído com finalidade educacional, como proposto pela disciplina. Os resultados que o sistema apresenta, mesmo os gerados pela IA, não têm validade clínica e não devem ser usados para diagnóstico real. Um sistema com esse propósito precisaria ser validado com datasets certificados, aprovado por órgãos regulatórios e testado extensivamente por profissionais de saúde antes de chegar a qualquer paciente.
